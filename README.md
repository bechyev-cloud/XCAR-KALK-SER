# XCAR — сервер синхронизации

Маленький сервер на чистом Node.js (без единой npm-зависимости), который
хранит полноценные аккаунты — **логин + пароль (с хешированием) + email +
телефон** — синхронизирует между устройствами машины, историю и настройки
из приложения XCAR, рассылает push-уведомления на другие телефоны того же
аккаунта при оформлении/завершении аренды, принимает заявки на оплату
подписки и хранит страницы чёрного списка.

## ⚠️ Если деплой на Render падает с ошибкой ENOENT `package.json`

Ошибка вида `npm error code ENOENT ... /opt/render/project/src/package.json`
означает одно из двух:

1. **Самая частая причина — неверный тип сервиса.** Папка `xcarpwa55`
   (само приложение — HTML/CSS/JS для телефона) — это **статический сайт**,
   в ней нет и не должно быть `package.json`. Если на Render создан **Web
   Service** и в качестве репозитория/папки указана `xcarpwa55` — сборка
   всегда будет падать именно с этой ошибкой, потому что Render пытается
   запустить `npm install` там, где нет `package.json`. Приложению-клиенту
   отдельный сервер вообще не нужен — оно просто открывается в телефоне и
   устанавливается как PWA. Если всё же хочется, чтобы клиент открывался по
   ссылке в браузере — создайте на Render не **Web Service**, а
   **Static Site** и укажите Publish Directory = `xcarpwa55` (Build Command
   можно оставить пустым).
   `package.json` есть **только** в папке `xcar-server` — вот её и нужно
   деплоить как Web Service (см. ниже).
2. **Неверный «Root Directory».** Если в одном git-репозитории лежат обе
   папки (`xcarpwa55` и `xcar-server`), а сервис на Render указывает на
   корень репозитория — в настройках сервиса (**Settings → Build & Deploy
   → Root Directory**) нужно явно прописать `xcar-server`, иначе Render
   ищет `package.json` не там, где он есть на самом деле.

Самый надёжный способ не ошибиться руками — задеплоить через **Blueprint**
(файл `render.yaml` из этой папки, способ 1 ниже): он сам создаёт сервис с
правильными настройками.

## Запуск локально

```
node server.js
```

По умолчанию слушает порт `3000`. Данные хранятся в файле `data/xcar.db.json`
рядом с сервером (создаётся автоматически). Пароли нигде не хранятся в
открытом виде — только хеш (scrypt + случайная соль на каждый аккаунт).

## Деплой на Render — с гарантией, что данные НЕ теряются

**Главное, что нужно понимать про Render:** обычный веб-сервис (в том числе
бесплатный тариф Free) хранит файлы на временном диске — он полностью
стирается при каждом передеплое и может стереться при перезапуске
контейнера. Чтобы данные (машины, история, аккаунты, push-подписки)
сохранялись по-настоящему надёжно, серверу нужен **постоянный диск
(Persistent Disk)**, а он на Render доступен только на платных тарифах —
подключить его к бесплатному сервису технически невозможно.

### Способ 1 (рекомендуется) — через Blueprint, диск подключается сам

В этой папке есть файл `render.yaml` — он полностью описывает сервис вместе
с постоянным диском, чтобы не забыть и не ошибиться при ручной настройке:

1. Залейте содержимое этой папки (вместе с `render.yaml`) в git-репозиторий.
2. На Render: **New → Blueprint**, укажите репозиторий.
3. Render сам создаст веб-сервис на платном тарифе (самом дешёвом,
   `0.5c-512mb`) с уже подключённым постоянным диском на 1 ГБ, смонтированным
   на `/data`, и с переменной `XCAR_DB_PATH=/data/xcar.db.json` — ничего
   вручную донастраивать не нужно, данные защищены сразу.
4. Нажмите Apply — через пару минут сервис будет готов.

Актуальные цены на платные тарифы Render — на [render.com/pricing](https://render.com/pricing).

### Способ 2 — вручную через Web Service

1. Залейте эту папку в отдельный git-репозиторий (или подпапку существующего).
2. На Render: **New → Web Service**, подключите репозиторий, выберите
   **платный тариф** (Free не подойдёт — на нём нельзя подключить диск).
3. Build Command: оставьте пустым или `npm install` (зависимостей нет, установка займёт секунду).
4. Start Command: `node server.js` (или `npm start`).
5. Откройте вкладку **Disks** у сервиса → **Add Disk**: например, имя
   `xcar-data`, точка монтирования `/data`, размер 1 ГБ.
6. Добавьте переменную окружения:
   ```
   XCAR_DB_PATH=/data/xcar.db.json
   ```
7. Остальные переменные окружения (необязательно):
   - `PORT` — порт (Render подставляет сам, ничего делать не нужно)
   - `XCAR_ALLOWED_ORIGIN` — если хотите ограничить CORS конкретным доменом
     вместо `*` (по умолчанию разрешены все источники, чего достаточно для PWA)

Если пропустить шаг с диском (или остаться на Free) — сервер всё равно
будет работать, но данные переживут только перезапуски самого процесса,
а не полный передеплой; рано или поздно они сотрутся.

После деплоя Render даст вам адрес вида `https://xcar-server-xxxx.onrender.com`
— именно его нужно вписать в приложении XCAR: **Меню → ⚙️ Настройки →
Серверы → ☁️ Render** (адрес сохранится как отдельный профиль сервера,
можно проверить пингом прямо там же).

> **⚠️ Важно, если вы уже разворачивали предыдущую версию этого сервера**
> (на аккаунтах «имя + PIN»): это несовместимое обновление контракта API.
> Старый сервер не будет работать с новым приложением (и наоборот) — поля
> запроса и правила проверки изменились (`name`/`pin` → `username`/`password`
> + необязательные `email`/`phone`). Нужно **передеплоить этот код** поверх
> старого сервиса на Render (просто запушьте новую версию в тот же
> репозиторий — Render передеплоит автоматически). Старые аккаунты, у кого
> они были заведены на PIN, не перейдут автоматически — их нужно будет
> зарегистрировать заново с логином и паролем.

## API

Формат `payload` везде одинаковый и совпадает с тем, что хранит приложение:
```json
{ "cars": [...], "history": [...], "settings": { "billingMode": "prepay" } }
```

### `GET /health`
Проверка, что сервис жив. Ответ: `{ "ok": true, "time": "..." }`

### `POST /api/register`
Тело: `{ "username": "idris", "password": "mypassword1", "email": "a@b.com", "phone": "+79281234567", "payload": {...} }`

`email` и `phone` необязательны. `payload` тоже необязателен — если не
передан, аккаунт создаётся с пустыми данными; приложение всегда передаёт
текущие локальные данные при регистрации, чтобы сразу перенести их на
сервер.

- `201` → `{ ok: true, username, email, phone, payload, updatedAt }`
- `409` → логин уже занят
- `400` → логин короче 2 символов, пароль короче 4 символов, либо email/телефон
  не проходят проверку формата

Логин хранится и сравнивается без учёта регистра. Пароль хешируется на
сервере (scrypt + соль) — открытый текст пароля никогда не попадает в
файл базы данных.

### `POST /api/login`
Тело: `{ "username": "idris", "password": "mypassword1" }`
- `200` → `{ ok: true, username, email, phone, payload, updatedAt }`
- `404` → аккаунт не найден (такого логина нет)
- `401` → неверный пароль

### `POST /api/sync`
Тело: `{ "username": "idris", "password": "mypassword1", "updatedAt": 1234567890, "payload": {...} }`

Это основной эндпоинт для фоновой синхронизации (раз в 30 секунд) и
потягивания вниз в Меню. Работает по принципу «последнее изменение
побеждает»:
- если `updatedAt` от клиента новее (или равен) того, что хранится на
  сервере — сервер сохраняет присланные данные;
- если на сервере уже есть более свежая версия — сервер возвращает её,
  ничего не перезаписывая, и клиент подтягивает эти данные себе.

- `200` → `{ username, email, phone, payload, updatedAt }` (актуальная
  версия данных после разрешения конфликта)
- `404` → аккаунт не найден (сначала нужно `/api/register`)
- `401` → неверный пароль

### `DELETE /api/account`
Тело: `{ "username": "idris", "password": "mypassword1" }`
Полностью удаляет аккаунт и все его данные с сервера.
- `200` → `{ ok: true }`
- `404` → аккаунт не найден
- `401` → неверный пароль

## Push-уведомления (Web Push)

Если на одном телефоне оформлена или завершена аренда, на остальных телефонах,
где выполнен вход в тот же аккаунт и включены push-уведомления (переключатель
в Настройках → Аккаунт), приходит системное уведомление — даже если приложение
не открыто в этот момент. Реализовано по стандарту Web Push (RFC 8291/8292,
VAPID) на встроенном `crypto` — без npm-пакета `web-push` — см. `webpush.js`.
Пара VAPID-ключей сервера создаётся автоматически при первом обращении и
хранится в той же базе данных.

### `GET /api/push/vapid-public-key`
Публичный VAPID-ключ сервера, нужен клиенту для подписки. Ответ: `{ "publicKey": "..." }`

### `POST /api/push/subscribe`
Тело: `{ "username": "idris", "password": "...", "subscription": { "endpoint": "...", "keys": { "p256dh": "...", "auth": "..." } } }`
Сохраняет push-подписку этого устройства (браузерный объект `PushSubscription.toJSON()`).
Одна и та же подписка (по `endpoint`) не дублируется.
- `200` → `{ ok: true }`
- `404`/`401` — аккаунт не найден / неверный пароль
- `400` — некорректная подписка

### `POST /api/push/unsubscribe`
Тело: `{ "username": "idris", "password": "...", "endpoint": "..." }`
Удаляет подписку конкретного устройства.
- `200` → `{ ok: true }`

### `POST /api/push/notify`
Тело: `{ "username": "idris", "password": "...", "title": "XCAR", "body": "Машина «Lada Vesta» оформлена в аренду", "excludeEndpoint": "..." }`
Рассылает уведомление на все подписанные устройства аккаунта, кроме
`excludeEndpoint` (обычно — устройство, которое и вызвало действие: ему
уведомление не нужно, у него данные и так уже актуальны). Подписки, которые
push-сервис отклонил как более не существующие (410/404 — например,
пользователь убрал разрешение на уведомления), автоматически удаляются.
- `200` → `{ ok: true, targeted, sent, failed }`
- `404`/`401` — аккаунт не найден / неверный пароль
- `400` — пустое сообщение

**Важно про доставку.** Реальная доставка push-уведомления зависит от сервиса
push-провайдера браузера (Google FCM для Chrome/Edge/Android, Apple для
Safari/iOS, Mozilla для Firefox) — серверу для этого не нужны никакие
дополнительные ключи или регистрация у Google/Apple, всё работает через
стандартный VAPID. Но для iOS Safari push-уведомления работают только если
приложение установлено на экран «Домой» как PWA (через «Поделиться» →
«На экран «Домой»»), а не открыто просто в браузере — это ограничение самой
iOS, а не этого сервера.

## Админ-панель (`/admin`) — подписки и чёрный список

Откройте `https://ваш-сервер.onrender.com/admin` в браузере. Там два раздела:

- **Заявки на подписку** — когда клиент в приложении нажимает «Я оплатил(а)»,
  заявка (ФИО, телефон, логин аккаунта, если есть) появляется здесь. Вы
  проверяете оплату по СБП/переводу и продлеваете подписку, указав логин
  аккаунта клиента и число дней.
- **Чёрный список** — загружаете HTML-страницу (или просто текст со списком
  клиентов, по одному на строку — этого достаточно, HTML необязателен) через
  форму или файлом. Клиенты в приложении в разделе «Чёрный список» смогут
  проверить имя/телефон — если есть совпадение в любой из загруженных
  страниц, оно покажется у них в приложении.

**Ключ администратора.** Панель защищена ключом — переменная окружения
`XCAR_ADMIN_KEY` на Render (**Environment** в настройках сервиса). Если её не
задать, используется ключ по умолчанию `idris-admin-2026` — **обязательно
задайте свой**, иначе панель сможет открыть кто угодно, кто знает ссылку.

### `POST /api/subscription/request`
Тело: `{ "username": "...", "name": "Иванов Иван", "phone": "+7..." }` —
отправляется из приложения автоматически при нажатии «Я оплатил(а)».

### `GET /api/admin/subscription/requests?key=...`
### `DELETE /api/admin/subscription/requests/:id?key=...`
### `POST /api/admin/subscription/extend` `{ "key":"...", "username":"...", "days":30 }`
Продлевает подписку аккаунта на `days` дней вперёд от текущей даты окончания
(или от сегодня, если уже истекла).

### `GET /api/blacklist/meta`
Публичный — дата последнего обновления и число загруженных страниц (это то,
что показывается в приложении рядом с кнопкой «Чёрный список»).

### `POST /api/blacklist/search` `{ "query": "Иванов" }`
Публичный — ищет по всем загруженным страницам, используется приложением.

### `GET /api/admin/blacklist/pages?key=...`
### `POST /api/admin/blacklist/upload` `{ "key":"...", "filename":"...", "html":"..." }`
### `DELETE /api/admin/blacklist/pages/:id?key=...`

**⚠️ Реквизиты для оплаты подписки** (номер карты, банк, телефон, получатель,
которые видит клиент в окне «Подписка» вместе с QR-кодом) заданы прямо в
`xcarpwa55/index.html` — найдите в самом конце файла константы
`SUBSCRIPTION_PRICE_TEXT`, `SUBSCRIPTION_BANK`, `SUBSCRIPTION_CARD_NUMBER`,
`SUBSCRIPTION_RECIPIENT`, `SUBSCRIPTION_PHONE` и замените на свои настоящие.

## Если хочется «настоящую» базу данных

Сейчас данные лежат в одном JSON-файле — этого с большим запасом хватает для
одного или нескольких пользователей (парк из нескольких десятков машин и
тысяч записей истории — это доли мегабайта). Вся работа с диском и хешированием
паролей изолирована в `db.js`: если в будущем понадобится Postgres/MySQL
(например, через Render Postgres), достаточно переписать функции в этом
одном файле — остальной код (`server.js`) их не касается.
