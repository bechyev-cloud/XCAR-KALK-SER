# XCAR — сервер синхронизации

Маленький сервер на чистом Node.js (без единой npm-зависимости), который
хранит полноценные аккаунты — **логин + пароль (с хешированием) + email +
телефон** — синхронизирует между устройствами машины, историю и настройки
из приложения XCAR, и рассылает push-уведомления на другие телефоны того же
аккаунта при оформлении/завершении аренды.

## Запуск локально

```
node server.js
```

По умолчанию слушает порт `3000`. Данные хранятся в файле `data/xcar.db.json`
рядом с сервером (создаётся автоматически). Пароли нигде не хранятся в
открытом виде — только хеш (scrypt + случайная соль на каждый аккаунт).

## Деплой на Render

1. Залейте эту папку в отдельный git-репозиторий (или подпапку существующего).
2. На Render: **New → Web Service**, подключите репозиторий.
3. Build Command: оставьте пустым или `npm install` (зависимостей нет, установка займёт секунду).
4. Start Command: `node server.js` (или `npm start`).
5. **Важно про хранение данных.** У обычного (Free/Starter) веб-сервиса на
   Render диск временный — при каждом передеплое или перезапуске контейнера
   файл `data/xcar.db.json` обнуляется. Чтобы данные не терялись, добавьте
   **Persistent Disk** в настройках сервиса (Render → Disks → Add Disk),
   примонтируйте его, например, на `/data`, и укажите переменную окружения:
   ```
   XCAR_DB_PATH=/data/xcar.db.json
   ```
   Без диска сервер тоже будет работать — просто данные переживут только
   перезапуски самого процесса, а не полный редеплой.
6. Переменные окружения (необязательно):
   - `PORT` — порт (Render подставляет сам, ничего делать не нужно)
   - `XCAR_DB_PATH` — путь к файлу базы данных (см. выше)
   - `XCAR_ALLOWED_ORIGIN` — если хотите ограничить CORS конкретным доменом
     вместо `*` (по умолчанию разрешены все источники, чего достаточно для PWA)

После деплоя Render даст вам адрес вида `https://xcar-server-xxxx.onrender.com`
— именно его нужно вписать в приложении XCAR: **Меню → ⚙️ Настройки →
Аккаунт и синхронизация → «Адрес сервера»**.

> **⚠️ Важно, если вы уже разворачивали предыдущую версию этого сервера**
> (на аккаунтах «имя + PIN»): это несовместимое обновление контракта API.
> Старый сервер не будет работать с новым приложением (и наоборот) — поля
> запроса и правила проверки изменились (`name`/`pin` → `username`/`password`
> + необязательные `email`/`phone`). Нужно **передеплоить этот код** поверх
> старого сервиса на Render (просто запушьте новую версию в тот же
> репозиторий — Render передеплоит автоматически). Старые аккаунты, у кого
> они были заведены на PIN, не перейдут автоматически — их нужно будет
> зарегистрировать заново с логином и паролем.

## API

Формат `payload` везде одинаковый и совпадает с тем, что хранит приложение:
```json
{ "cars": [...], "history": [...], "settings": { "billingMode": "prepay" } }
```

### `GET /health`
Проверка, что сервис жив. Ответ: `{ "ok": true, "time": "..." }`

### `POST /api/register`
Тело: `{ "username": "idris", "password": "mypassword1", "email": "a@b.com", "phone": "+79281234567", "payload": {...} }`

`email` и `phone` необязательны. `payload` тоже необязателен — если не
передан, аккаунт создаётся с пустыми данными; приложение всегда передаёт
текущие локальные данные при регистрации, чтобы сразу перенести их на
сервер.

- `201` → `{ ok: true, username, email, phone, payload, updatedAt }`
- `409` → логин уже занят
- `400` → логин короче 2 символов, пароль короче 4 символов, либо email/телефон
  не проходят проверку формата

Логин хранится и сравнивается без учёта регистра. Пароль хешируется на
сервере (scrypt + соль) — открытый текст пароля никогда не попадает в
файл базы данных.

### `POST /api/login`
Тело: `{ "username": "idris", "password": "mypassword1" }`
- `200` → `{ ok: true, username, email, phone, payload, updatedAt }`
- `404` → аккаунт не найден (такого логина нет)
- `401` → неверный пароль

### `POST /api/sync`
Тело: `{ "username": "idris", "password": "mypassword1", "updatedAt": 1234567890, "payload": {...} }`

Это основной эндпоинт для фоновой синхронизации (раз в 30 секунд) и
потягивания вниз в Меню. Работает по принципу «последнее изменение
побеждает»:
- если `updatedAt` от клиента новее (или равен) того, что хранится на
  сервере — сервер сохраняет присланные данные;
- если на сервере уже есть более свежая версия — сервер возвращает её,
  ничего не перезаписывая, и клиент подтягивает эти данные себе.

- `200` → `{ username, email, phone, payload, updatedAt }` (актуальная
  версия данных после разрешения конфликта)
- `404` → аккаунт не найден (сначала нужно `/api/register`)
- `401` → неверный пароль

### `DELETE /api/account`
Тело: `{ "username": "idris", "password": "mypassword1" }`
Полностью удаляет аккаунт и все его данные с сервера.
- `200` → `{ ok: true }`
- `404` → аккаунт не найден
- `401` → неверный пароль

## Push-уведомления (Web Push)

Если на одном телефоне оформлена или завершена аренда, на остальных телефонах,
где выполнен вход в тот же аккаунт и включены push-уведомления (переключатель
в Настройках → Аккаунт), приходит системное уведомление — даже если приложение
не открыто в этот момент. Реализовано по стандарту Web Push (RFC 8291/8292,
VAPID) на встроенном `crypto` — без npm-пакета `web-push` — см. `webpush.js`.
Пара VAPID-ключей сервера создаётся автоматически при первом обращении и
хранится в той же базе данных.

### `GET /api/push/vapid-public-key`
Публичный VAPID-ключ сервера, нужен клиенту для подписки. Ответ: `{ "publicKey": "..." }`

### `POST /api/push/subscribe`
Тело: `{ "username": "idris", "password": "...", "subscription": { "endpoint": "...", "keys": { "p256dh": "...", "auth": "..." } } }`
Сохраняет push-подписку этого устройства (браузерный объект `PushSubscription.toJSON()`).
Одна и та же подписка (по `endpoint`) не дублируется.
- `200` → `{ ok: true }`
- `404`/`401` — аккаунт не найден / неверный пароль
- `400` — некорректная подписка

### `POST /api/push/unsubscribe`
Тело: `{ "username": "idris", "password": "...", "endpoint": "..." }`
Удаляет подписку конкретного устройства.
- `200` → `{ ok: true }`

### `POST /api/push/notify`
Тело: `{ "username": "idris", "password": "...", "title": "XCAR", "body": "Машина «Lada Vesta» оформлена в аренду", "excludeEndpoint": "..." }`
Рассылает уведомление на все подписанные устройства аккаунта, кроме
`excludeEndpoint` (обычно — устройство, которое и вызвало действие: ему
уведомление не нужно, у него данные и так уже актуальны). Подписки, которые
push-сервис отклонил как более не существующие (410/404 — например,
пользователь убрал разрешение на уведомления), автоматически удаляются.
- `200` → `{ ok: true, targeted, sent, failed }`
- `404`/`401` — аккаунт не найден / неверный пароль
- `400` — пустое сообщение

**Важно про доставку.** Реальная доставка push-уведомления зависит от сервиса
push-провайдера браузера (Google FCM для Chrome/Edge/Android, Apple для
Safari/iOS, Mozilla для Firefox) — серверу для этого не нужны никакие
дополнительные ключи или регистрация у Google/Apple, всё работает через
стандартный VAPID. Но для iOS Safari push-уведомления работают только если
приложение установлено на экран «Домой» как PWA (через «Поделиться» →
«На экран «Домой»»), а не открыто просто в браузере — это ограничение самой
iOS, а не этого сервера.

## Если хочется «настоящую» базу данных

Сейчас данные лежат в одном JSON-файле — этого с большим запасом хватает для
одного или нескольких пользователей (парк из нескольких десятков машин и
тысяч записей истории — это доли мегабайта). Вся работа с диском и хешированием
паролей изолирована в `db.js`: если в будущем понадобится Postgres/MySQL
(например, через Render Postgres), достаточно переписать функции в этом
одном файле — остальной код (`server.js`) их не касается.
